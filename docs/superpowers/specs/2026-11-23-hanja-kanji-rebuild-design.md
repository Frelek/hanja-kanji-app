# Hanja & Kanji Learner — Rebuild Design

Date: 2026-11-23
Status: draft for approval
Repo: `Frelek/hanja-kanji-app` (GitHub Pages, branch `main`, served from `/`)
Live: https://frelekkacper.com/hanja-kanji-app/

## 1. Intent

Two people, Kacper and his girlfriend, are learning **Japanese and Korean from the
beginning**, through their characters. They use the app as an iPhone home-screen app
and in a laptop browser.

The current app was generated by another AI and is not fit for that purpose:

- **Family trees are wrong.** Of 173 hanja that have a parent, only 64 contain it. The
  rest are grouped by topic (四←一, 前/後/東/西←中, 校←室, 茶←米, 藥←茶), and 驛's parent
  is a category ID. The kanji file has the same problem (51 of 153). The `components`
  lists are wrong too (華 = 艹+十, 四 = 口).
- **Korean example words never show hanja.** All 265 are written in hangul only, so the
  learner never sees the character used in a word.
- **The scheduler damages itself.** "Hard" resets a card to 1 day. When nothing is due,
  it quizzes every learned card and reschedules all of them. "Learned" is a manual
  checkbox.
- **It is not offline.** Stroke data comes from jsdelivr and fonts from Google.
- **No profiles and no sync.** It doesn't follow a recognised curriculum. It looks
  generated: emoji everywhere, menus mixing Korean, Japanese and English, "280+" badges.

The rebuild should teach correctly, work like Anki, look crafted, and keep both
people's progress in sync across their devices.

**Success looks like this:** both open it daily, work through an Anki-style queue,
trust every reading, tree and example word, and find their progress on whichever
device they pick up.

## 2. Goals

1. **Curriculum**
   - Japanese: JLPT **N5 → N4 → N3**, every kanji of each level (~612).
   - Korean: 한국어문회 한자능력검정시험 **8급 → 7급 → 6급 → 5급** in full (500
     characters; the Ⅱ levels sit inside their parent level), plus the **110 most
     common 4급Ⅱ characters**, for **610** in total.
2. **Correct trees.** A parent → child link means the parent really is a graphical
   component of the child.
3. **Learning engine that works like Anki,** scheduled with **FSRS**.
4. **Profiles and sync.** Profiles are `name#1234` with no password. Sync goes through a
   private GitHub repo.
5. **Fully offline PWA.** Fonts, stroke data, libraries and character data are all
   bundled.
6. **"Paper & ink" visual design,** with characters in textbook handwriting
   (**Klee One**).

## 3. Non-goals

- No passwords or real accounts. `name#tag` is considered enough protection by the
  users.
- No native or App Store app.
- No connection to the Anki app or AnkiWeb. The app *works like* Anki; it does not
  *talk to* it.
- No levels beyond N3 or past the 4급Ⅱ subset for now. The data pipeline should make
  adding N2 or 4급 a config change.
- No social features, leaderboards or sharing.
- Meanings and menus are in English only.
- No migration of progress from the old app (see §9).

## 4. Anti-goals: failure even if it "works"

- **Data written by hand or by an AI.** Every reading, meaning, component and example
  word comes from a named dictionary source through a reproducible script, and is
  checked by automated validation.
- **Decoration.** Emoji, badge counters, menus in mixed languages.
- **Losing or corrupting progress.** Sync overwrites, practice sessions rescheduling
  cards, resets that cannot be undone on the server.
- **Needing the internet to study.**

## 5. Constraints

- **Static hosting only.** GitHub Pages at `/hanja-kanji-app/`. All paths stay relative
  (`./`) so the app works under a subfolder.
- **No build step.** Plain modern JavaScript (ES modules), with libraries vendored into
  the repo as files: Preact + htm (the single `htm/preact/standalone` module) and
  `ts-fsrs` **5.4.2** (FSRS-6; the 6.x release is split into chunks with an external
  dependency, so it can't be vendored as one file). Stroke animation is a small SVG animator written for this app (§7.1.5);
  HanziWriter is dropped. Nothing is loaded from a CDN at runtime.
- **iOS home-screen PWA limits.** No background sync, so syncing happens while the app
  is open. Data lives in **IndexedDB** (localStorage's ~5 MB is too small for multi-year
  review logs). Home-screen web apps keep their storage. Safari's 7-day eviction does
  not apply to them.
- **Sync token.** A GitHub fine-grained personal access token with *Contents:
  read/write* on **one private repo only**. The user creates it and pastes it on each
  device. It is stored only in that device's IndexedDB. It is never committed, logged or
  put in a URL.
- **Licences.** Data and font sources have attribution requirements:
  - kanji-data uses KANJIDIC data, CC BY-SA (EDRDG);
  - animCJK uses the Arphic Public License and LGPL;
  - the JLPT decks are MIT;
  - kengdic carries its own licence;
  - the 급수 lists are © 한국어문회, used privately;
  - cjkvi data carries its own licences;
  - Klee One and Gowun Batang use the OFL.

  All are credited on
  an About screen. The builder verifies each source's licence before using it.

## 6. Approaches considered

**How the app is built** (picked: **1**)

1. **Clean rewrite with no build step.** Vanilla ES modules + Preact/htm, vendored. Files
   deploy as-is, and pure logic is tested with Node's built-in test runner. *Picked:* it
   has nothing to install or compile, a push goes live, and it is enough structure for a
   two-person app.
2. **Rewrite with Vite + TypeScript.** Strongest type checking, but every change needs a
   build and deploys go through GitHub Actions. More moving parts than this app needs.
   *Rejected by the user.*
3. **Patch the existing code.** It is built around a manual "learned" flag, one store per
   language and no profiles. Every new feature fights it. *Rejected.*
4. **Native iOS app.** Installing outside the App Store needs a paid Apple developer
   account, or a reinstall every 7 days. *Rejected.*

**Sync backend** (picked: **GitHub repo + token**)

- **GitHub repo + token.** Uses what the user already has. Every sync is a commit, so the
  history doubles as a backup. Cost: a one-time token paste per device, and renewing the
  token when it expires.
- **Cloudflare Worker + database.** No setup on devices, but one more account.
- **Supabase.** Free tier pauses after a week of inactivity.
- **The user's own PC.** Only syncs while it's on.

**Character font** (picked: **Klee One**, textbook handwriting)

- Klee One shows how strokes are really written and stays very legible. Brush (Yuji
  Syuku) is harder to read small. Felt-pen (Zen Kurenaido) is imprecise about stroke
  shapes.

**Overall look** (picked: **Paper & ink**)

- Calm paper background with ink-black text. Menus use the system sans-serif font, and
  the handwritten characters are the only decoration. The alternative was a "school
  workbook" look: grid paper, red guides, handwriting everywhere.

## 7. Design

### 7.1 Curriculum data

**Sources.** Everything is downloaded by the build script into a git-ignored `sources/`
folder.

These sources were confirmed during planning (§12).

| What | Source |
|---|---|
| JLPT kanji levels | Jonathan Waller's lists as packaged in `davidluzgouveia/kanji-data` (`jlpt_new`). Confirmed: N5 79, N4 166, N3 367 = 612. |
| Japanese meanings, stroke counts, frequency | `kanji-data` (from KANJIDIC). |
| Jōyō readings | `cjkvi/cjkvi-tables` `joyo2010.txt`, the official 2010 table. It covers all 612. |
| Japanese example words | `jamsinclair/open-anki-jlpt-decks` `src/n5.csv`…`n1.csv` (MIT). These cover all 612 at some level; JMdict is not needed. |
| 한국어문회 levels and official 훈음 | `rycont/hanja-grade-dataset` `hanja.csv`, converted from 한국어문회's own xls, with Ⅱ sub-levels and multiple 훈음. It is cross-checked against animCJK's `hanja8`–`hanja5` sets: identical 500 characters after NFC normalisation. |
| Korean English meaning | animCJK `dictionaryKo.txt` `definition` (Unihan-derived); `dictionaryZhHant.txt` for 4급Ⅱ characters missing from it. |
| Korean example words (with hanja + English) | kengdic (`garfieldnate/kengdic`): hanja column, plus `level` A/B/C/D from the national learner word list. |
| Character decomposition | `cjkvi/cjkvi-ids` (IDS sequences) |
| Stroke order, Japanese | animCJK `graphicsJa.txt`: Japanese forms in Japanese school order (based on KanjiVG). It covers all 612. |
| Stroke order, Korean | animCJK `graphicsKo.txt`: Korean order, covering all of 8급–5급 and 20 of 4급Ⅱ. Fallback: animCJK `graphicsZhHant.txt` (traditional forms). |
| Fonts | Klee One (characters, Japanese), Gowun Batang (hangul), from `google/fonts`, subset with `pyftsubset` to the characters actually used |

**Pipeline.** `tools/build_data.py` reads the sources and writes `data/ja.json`,
`data/ko.json`, `data/strokes/ja/<char>.json` and `data/strokes/ko/<char>.json`. Strokes are
stored per language because the same character can be written differently in each. The generated files are committed, so the
site needs no build. Running it twice gives byte-identical output.

**Character record**, common shape (language-specific fields marked):

```jsonc
{
  "id": "ja:休",            // "<lang>:<char>", stable forever (used in review logs)
  "char": "休",
  "level": "N5",            // ko: "8급" | "7급" | "6급" | "5급" | "4급Ⅱ"
  "sublevel": null,         // ko only: "7급Ⅱ", "6급Ⅱ", "5급Ⅱ" when applicable
  "order": 57,              // position in the global study order (§7.1.2)
  "strokes": 6,
  "meanings": ["rest", "day off", "absence"],   // at most 3, most important first
  "on": ["キュウ"],          // ja only, katakana, Jōyō readings only
  "kun": ["やす.む", "やす.まる", "やす.める"],  // ja only, hiragana, "." marks okurigana, Jōyō only
  "hunEum": [{ "hun": "쉴", "eum": "휴" }],   // ko only: official 훈음, first is the main one
                                            // e.g. 金: [{쇠, 금}, {성, 김}]
  "parts": [                // direct visual parts, for display
    { "char": "亻", "meaning": "person", "ref": "ja:人" },
    { "char": "木", "meaning": "tree",   "ref": "ja:木" }
  ],
  "parents": ["ja:人", "ja:木"],   // in-set characters it is built from (§7.1.1)
  "primaryParent": "ja:木",        // where it hangs in the tree view
  "words": [                // 2–3, best first
    { "w": "休日", "kana": "きゅうじつ", "en": "holiday", "level": "N5" }
    // ko: { "w": "休日", "hangul": "휴일", "en": "holiday" }
  ],
  "sentence": null,         // optional, see §7.1.3
  "hasStrokes": true
}
```

#### 7.1.1 Trees

- **Decomposition.** Each character is decomposed recursively through IDS. Radical
  variants are mapped to their full form *for linking only*: 亻→人, 氵→水, 扌→手,
  忄→心, 灬→火, 礻→示, 衤→衣, 訁→言, 飠→食, 釒→金, 糹→糸, 艹→艸, 辶→辵, 刂→刀, and
  so on. The display keeps the variant ("亻 person"). Ambiguous forms (月 as moon or as
  flesh, 阝 left/right, 王/玉) are resolved per character from the IDS source. Where the
  source doesn't settle it, the character gets no link rather than a guessed one.
- **Parents** are the *largest* in-set characters found in the decomposition. If 林 and
  木 both appear in 森, the parent is 林, because 林 already contains 木. A character can
  have several parents (休 = 人 + 木). The structure is a DAG, not a tree.
- **Display.** Each character hangs under its `primaryParent`. Other parents show as
  "also 人 ✓". The rule for choosing the primary parent is left to the builder (suggested:
  the largest component, with ties going to the semantic radical). Characters with no
  in-set parent are roots.
- **Cross-level parents.** A parent from the *same or an earlier* level is required. A
  parent from a *later* level (an N5 kanji containing an N4 kanji) is shown as a part
  labelled "comes in N4". It does **not** lock the child, so every level keeps its exact,
  complete stock.
- **Parts that aren't study characters** (氵, 宀, 交…) show with their meaning, but are
  not cards.

#### 7.1.2 Study order

- Levels are studied in order: N5 before N4 before N3; 8급 → 7급 → 6급 → 5급 → 4급Ⅱ
  subset.
- Korean Ⅱ sub-levels come first within their level: 7급Ⅱ before the rest of 7급, 6급Ⅱ
  before the rest of 6급, 5급Ⅱ before the rest of 5급.
- Within a level (or sub-level), the order is topological (required parents before
  children), then by frequency (KANJIDIC frequency for Japanese, the selection metric
  below for Korean). A required parent always comes first, even across a sub-level.
- **Picking the 110 4급Ⅱ characters.** Rank all 250 4급Ⅱ characters by how many
  Sino-Korean dictionary words (kengdic) contain them, and take the top 110. The builder
  may substitute a better Korean frequency source if one is found; it must be documented.

#### 7.1.3 Example words and sentences

- **Japanese.** 2–3 words containing the kanji. Prefer words from the JLPT vocabulary
  list at the kanji's level or lower, and whose other kanji are at that level or lower.
  Fall back to JLPT-list words from any level whose kanji are all in N5–N3, then the
  single-kanji word itself. Expressions listed as "川; 河" are split on `;`. **Every word carries pure kana** (`kana`), shown
  directly below it. This rule carries over from the old spec.
- **Korean.** 2–3 Sino-Korean words **written in hanja**, with hangul and English (學校 /
  학교 / school). Prefer words whose other hanja are at the same level or lower, then
  shorter, more common words.
- **Sentences** are nice-to-have, built last (phase 5). They would be one Tatoeba
  sentence per character where a short, clean one exists. Japanese sentences get a kana
  reading generated at build time by a tokenizer. Characters without a good sentence
  simply show none.

#### 7.1.4 Validation

`tests/data.test.js` fails the build if any of these break:

- Level lists are complete: every listed character appears exactly once. The counts match
  the source lists and 610 for Korean.
- Every `parents` entry really appears in the character's decomposition. The structure has
  no cycles, and no required parent comes from a later level.
- Every Japanese word has `kana`. Every word actually contains its character. Every Korean
  word contains hanja.
- Every character has stroke data **for its own language**. animCJK's Japanese set covers all 612
  kanji, so the Japanese allowlist must be empty. Any Korean character missing from both
  Korean sources goes on an explicit allowlist and shows a static glyph with "stroke order
  not available". The validation report prints that list.
- Japanese readings are all Jōyō readings. Every Korean character has at least one
  official 훈음.
- Every character used anywhere has a glyph in the bundled subset font. Missing glyphs
  fall back to a subset of Noto Serif KR or JP, and validation reports them.

#### 7.1.5 Stroke order and animation

- Stroke order must be **correct for each language**. Showing Chinese stroke order to a
  Japanese learner counts as wrong data (§4). The reviewer found that 56 of the 612
  N5–N3 kanji (毎, 気, 読, 駅, 楽…) are missing from hanzi-writer-data, because they are
  Japanese simplified forms. The characters it does have use Chinese order.
- Stroke files store each stroke as a **centre line** in drawing order (animCJK's
  "medians": point lists in a 1024-unit box with y pointing up). Stroke numbers come from
  that order.
- The animator draws each centre line in order with a round-capped, ink-coloured stroke,
  using `stroke-dashoffset`. It looks like a pen writing, which suits the textbook
  handwriting font. It offers play, replay, step-by-step and stroke numbers. It respects
  `prefers-reduced-motion`, and then shows the finished character with numbers instead.

#### 7.1.6 Readings and meanings shown

- **Japanese:** only the **Jōyō readings**, the official set taught in Japanese schools
  and used in normal text. That removes the rare and archaic readings KANJIDIC also lists
  (生 has 18 kun readings in KANJIDIC). On the card back, the first on reading and the
  first kun reading are shown large, and the others smaller beneath them.
- **Meanings:** at most 3 English meanings, taken in source order (kanji-data for Japanese, animCJK definitions for Korean).
- **Korean:** all official 훈음 for the character. The first is the main one, shown large
  (金 → 쇠 금); the others are shown smaller (성 김).

### 7.2 Learning engine (how it mirrors Anki)

**Cards.** One *recognition* card per character, per language, per profile. The front
shows the character; the back shows readings, meaning, parts and example words. There is
no writing card type in v1. The detail sheet can replay the stroke animation, but per the
old rule there is no quiz inside it.

**Card life cycle**, as in Anki: **new → learning → review**, and **relearning** after a
lapse.

| Setting | Default | Where |
|---|---|---|
| New cards per day | 10 | per language, per profile |
| Maximum reviews per day | 200 | per language, per profile |
| Learning steps | 1m 10m | Settings |
| Relearning steps | 10m | Settings |
| Desired retention | 0.90 (range 0.80–0.95) | Settings |
| Next day starts at | 04:00 local | Settings |
| Leech threshold | 8 lapses: tagged and listed in Stats, **not** suspended | fixed |

- **Scheduler.** Vendored `ts-fsrs` (FSRS-6) with default parameters. Training the
  parameters on the user's own history is **out of scope for v1** (§10).
- **Daily queue.** First, learning and relearning cards that are due now. Then reviews
  that are due, then today's new cards, interleaved with reviews (one new card after every
  few reviews). Learning cards come back during the session when their step expires. If
  nothing is left but learning cards waiting on a timer, the screen shows "next card in
  3 min".
- **Where new cards come from.** The next characters in study order (§7.1.2) whose
  required parents have **already been introduced**, meaning studied at least once.
- **Answer buttons.** Again / Hard / Good / Easy, each showing its next interval (`<1m`,
  `6m`, `10m`, `3d`…) computed by ts-fsrs. On a laptop: Space to show the answer, 1–4 to
  rate.
- **Undo** the last answer, within the session. It appends
  `{ "type": "undo", "target": "<entry id>" }`, and replay skips the targeted answer.
  That keeps the log append-only even if the answer was already synced.
- **Practice this level** (replaces the old "category quiz", same place: top of the
  level). It quizzes already-introduced cards of that level **without changing their
  schedule**, like Anki's custom study with rescheduling off. Rules carried over from the
  old spec: never practise characters that haven't been introduced, and never put a quiz
  button on single characters.

**Review log is the source of truth.** Every answer appends:

```jsonc
{ "id": "<deviceId>-<ms>-<n>", "card": "ja:休", "rating": 3,
  "at": "2026-11-23T08:12:03.120Z", "ms": 4200, "dev": "<deviceId>", "type": "review" }
```

Card state is derived by **replaying the log through ts-fsrs** in timestamp order. The
replay is deterministic, so two devices that hold the same log hold the same schedule. The
derived states are cached in IndexedDB and rebuilt whenever the log changes from a merge.
Practice-mode answers are not logged as reviews.

**Reset** of one language appends `{ "type": "reset", "lang": "ja", "at": … }`, and
replay ignores earlier entries for that language. The server history is never deleted.

**Stats screen:** reviews today, streak, true retention over the last 30 days, a 7-day due
forecast, per-level progress, and the list of leeches.

### 7.3 Profiles and sync

**On the device**

- **First launch** shows "Who's studying?": the profiles already on this device, plus
  **Add profile**. Add profile takes a name (1–20 letters or digits) and a 4-digit tag.
  `Kacper#1234` and `kacper#1234` are the same profile (the key is case-insensitive), and
  the display keeps the typed case.
- **Switching.** Profiles are switched from Settings. The app remembers the last active
  profile.
- **Sync is optional.** Without a token the app works fully, with status "Sync off".
- **Connecting.** Settings → Sync: paste the token. The repo field is pre-filled as
  `Frelek/hanja-kanji-progress` and can be changed. One token per device, shared by all
  profiles on it. The token is tested immediately, and the result is reported in plain
  words.

**Repo layout** (private repo, created by the user)

```
profiles/<name-lowercase>-<tag>/profile.json       # display name, tag, created, settings (+updatedAt per field)
profiles/<name-lowercase>-<tag>/log-YYYY-Www.json  # that ISO-8601 week's review-log entries (UTC, week-based year), append-only
```

Weekly files, written as compact JSON, keep each file small: a week of heavy study
(1,500 answers) is ~200 KB, far below the Contents API's 1 MB read limit, and ten years
is ~520 files, under the 1,000-entry directory listing limit.

**Adding a profile that already exists on the server** downloads it, replays it and
greets with "Welcome back". A profile that doesn't exist yet is created.

**Sync procedure** (GitHub Contents API, `api.github.com`, CORS-enabled)

1. List the profile folder and compare each file's `sha` with the last synced `sha`.
2. Download the changed weeks.
3. **Merge the logs:** the union by entry `id`, so merging is idempotent and the order of
   merges doesn't matter.
4. Merge settings field by field: the newest `updatedAt` wins.
5. Upload local entries that aren't on the server yet into the right week file, with a
   `sha` precondition.
6. On a conflict (409/422): fetch again, merge, retry, up to 3 times.
7. If any entries changed, replay the log.

**When it syncs:** on app open, on return to the foreground and on leaving it (best
effort), when the connection comes back, at the end of a study session, after every 20
answers, and from a **Sync now** button.

**Status line** on Home: "Synced 2 min ago" (then "Synced 3 h ago", "Synced 2 d ago") ·
"Offline: 23 answers waiting" · "Sync problem: token refused, tap to fix". Errors never
block studying.

### 7.4 Screens (Paper & ink)

These follow the mockups the user approved. Tabs: **Study · Characters · Stats ·
Settings**.

- **Profile picker.** The profiles on the device, plus Add profile.
- **Study (home).** Profile chip and sync status. Language switch (日本語 | 한국어). A
  "Today" card with New, Learning and Review counts in Anki's blue, red and green, a
  **Study now** button and an estimated time. Then a progress list per level (N5 62/79…).
- **Study session.**
  - Front: the character large inside a practice-grid box (田字格). Tap or press Space to
    reveal.
  - Back, for Japanese: On reading in katakana, Kun reading in hiragana with an okurigana
    dot (やす・む), meaning, parts (亻 person + 木 tree), and 2–3 word tiles with a kana
    pill under each word.
  - Back, for Korean: 훈음 (쉴 휴), English meaning, parts, and word tiles (休日 / 휴일 /
    holiday).
  - Rating buttons with intervals, a progress bar, the count left, undo, and exit.
- **Characters.**
  - Level chips (N5 N4 N3 / 8급 7급 6급 5급 4급Ⅱ) and the **Practice this level** button.
  - Family trees with node states: *studied ✓*, *new* (available), *later* (shows "needs
    日").
  - Tapping any node opens the **detail sheet**. Locked characters can be viewed, but not
    studied early. The sheet shows the large character with a stroke animation and a
    replay button, readings, meaning, parts (linked when they are characters), words, an
    optional sentence, and the card status ("next review in 12 days").
- **Stats.** As in §7.2.
- **Settings.**
  - Profile: switch or add.
  - Sync: token, repo, Sync now, last sync time.
  - Study: the settings from §7.2.
  - Appearance: light, dark or auto.
  - About: data sources and licences.
  - Reset progress, per language, with confirmation.
- **Typography.**
  - Klee One SemiBold for all CJK characters and Japanese text.
  - Gowun Batang for hangul.
  - System sans-serif for the English UI.
  - All fonts bundled as subsets.
- **Colour.** Paper `#f6f1e7`, ink `#1f1b17`, secondary text `#776c60`, hairlines
  `#e2d8c8`, cards `#fffcf6`. The primary button is ink-black. There is a matching dark
  theme (auto from `prefers-color-scheme`, with a manual override). Text contrast meets
  WCAG AA, tap targets are ≥ 44 px, and `prefers-reduced-motion` is respected.
- **Never:** emoji, badge counters, or mixed-language menu labels. Korean and Japanese
  appear only as learning content and in the language switch.

### 7.5 Offline and PWA

- The service worker precaches the app shell, vendored libraries, both data files, the
  font subsets and all stroke files (~1,200 × a few KB). The cache is versioned. When a
  new version is installed, the app shows "Update available, reload".
- The manifest keeps relative `start_url` and `scope`, `display: standalone`, theme colours
  matching Paper & ink, and new icons in the same style.
- The stroke animator loads `./data/strokes/<lang>/<char>.json` from the cache.

## 12. Updates made while planning

- **Sources were swapped for ones that check out:**
  - Japanese strokes come from animCJK's Japanese set (same format as the Korean set, and
    covers all 612), not raw KanjiVG.
  - The 급수 lists come from `rycont/hanja-grade-dataset`, and they match animCJK
    exactly.
  - The Jōyō readings table comes from `cjkvi-tables`.
  - KANJIDIC2, JMdict, Unihan and libhangul downloads are no longer needed.
- **Five 급수 characters (金 車 樂 不 宅) appear as CJK compatibility code points** in the
  source. All text is NFC-normalised on input.
- **Korean word matching needs a small variant map**, for example 强→強 and 畵→畫, because
  kengdic sometimes uses the other form.
- **Undo is an appended entry,** not a deletion (§7.2).
- **Final review (R33–R35):**
  - Sync log files are weekly (`log-YYYY-Www.json`, ISO-8601 week of the entry's UTC
    time) and compact JSON, instead of monthly: a monthly file of heavy study outgrew the
    Contents API's 1 MB read limit within about two months. The repo had no data yet, so
    no migration is needed.
  - A refused token reads "Sync problem: token refused, tap to fix", not "token expired":
    a 403 can also be a read-only token.
  - The status line adds "Synced N h ago" and "Synced N d ago".
